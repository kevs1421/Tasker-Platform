   137→   137→## 4. Production Build & Deployment
   138→   138→
   139→   139→### Build
   140→   140→
   141→   141→```bash
   142→   142→bun run build
   143→   143→```
   144→   144→
   145→   145→This command performs two steps:
   146→   146→
   147→   147→1. **`next build`** — Compiles the Next.js application in standalone output mode. All required dependencies, traces, and server code are bundled into `.next/standalone/`.
   148→   148→2. **Asset copy** — Copies `.next/static` and `public/` into the standalone directory so all assets are self-contained:
   149→   149→
   150→   150→```bash
   151→   151→cp -r .next/static .next/standalone/.next/
   152→   152→cp -r public .next/standalone/
   153→   153→```
   154→   154→
   155→   155→### Start the Production Server
   156→   156→
   157→   157→```bash
   158→   158→bun run start
   159→   159→```
   160→   160→
   161→   161→This runs:
   162→   162→
   163→   163→```bash
   164→   164→NODE_ENV=production bun .next/standalone/server.js
   165→   165→```
   166→   166→
   167→   167→The server listens on **port 3000** by default. Logs are written to both stdout and `server.log`.
   168→   168→
   169→   169→### Standalone Output Mode
   170→   170→
   171→   171→The `next.config.ts` sets `output: "standalone"`, which means:
   172→   172→
   173→   173→- The build produces a **self-contained server** in `.next/standalone/`
   174→   174→- Only `node_modules` required at runtime are traced and included
   175→   175→- No need to install `node_modules` on the production server after building
   176→   176→- The standalone directory contains its own `node_modules/`, `.next/`, and `server.js`
   177→   177→
   178→   178→This is ideal for Docker containers, VMs, and bare-metal deployments where you want a minimal footprint.
   179→   179→
   180→   180→### File Storage Configuration
   181→   181→
   182→   182→Uploaded files are stored in the local `upload/` directory relative to the project root (`process.cwd()`).
   183→   183→
   184→   184→| Setting | Value |
   185→   185→|---|---|
   186→   186→| **Upload directory** | `upload/` (relative to CWD) |
   187→   187→| **Max file size** | 10 MB |
   188→   188→| **Allowed extensions** | `.jpg`, `.jpeg`, `.png`, `.gif`, `.webp`, `.svg`, `.pdf`, `.doc`, `.docx`, `.xls`, `.xlsx`, `.txt`, `.zip` |
   189→   189→| **Filename format** | `{uuid}-{sanitized-original-name}` |
   190→   190→| **Serving** | Rewritten via `next.config.ts`: `/upload/:path*` → `/api/upload/serve/:path*` |
   191→   191→
   192→   192→#### Important for Production
   193→   193→
   194→   194→After building with standalone mode, the `upload/` directory **must exist at the working directory** where the server runs. Ensure:
   195→   195→
   196→   196→```bash
   197→   197→# Create the upload directory if it doesn't exist
   198→   198→mkdir -p /opt/taskflow/upload
   199→   199→
   200→   200→# Set appropriate permissions
   201→   201→chmod 750 /opt/taskflow/upload
   202→   202→```
   203→   203→
   204→   204→When deploying the standalone build, the `upload/` directory must be **alongside** the standalone output, or you must set the working directory appropriately:
   205→   205→
   206→   206→```bash
   207→   207→# Option A: Run from project root (upload/ is already there)
   208→   208→cd /opt/taskflow
   209→   209→NODE_ENV=production bun .next/standalone/server.js
   210→   210→
   211→   211→# Option B: If deploying only the standalone directory, symlink or copy upload/
   212→   212→mkdir -p /opt/taskflow/.next/standalone/upload
   213→   213→# Or bind-mount in Docker: -v /opt/taskflow/upload:/app/upload
   214→   214→```

   300→   300→## 6. Caddy / Reverse Proxy Configuration
   301→   301→
   302→   302→### Overview
   303→   303→
   304→   304→TaskFlow includes a `Caddyfile` that configures Caddy as a reverse proxy. The current configuration uses the **XTransformPort gateway pattern** for dynamic port routing.
   305→   305→
   306→   306→### Current Caddyfile
   307→   307→
   308→   308→```caddyfile
   309→   309→:81 {
   310→   310→    @transform_port_query {
   311→   311→        query XTransformPort=*
   312→   312→    }
   313→   313→
   314→   314→    handle @transform_port_query {
   315→   315→        reverse_proxy localhost:{query.XTransformPort} {
   316→   316→            header_up Host {host}
   317→   317→            header_up X-Forwarded-For {remote_host}
   318→   318→            header_up X-Forwarded-Proto {scheme}
   319→   319→            header_up X-Real-IP {remote_host}
   320→   320→        }
   321→   321→    }
   322→   322→
   323→   323→    handle {
   324→   324→        reverse_proxy localhost:3000 {
   325→   325→            header_up Host {host}
   326→   326→            header_up X-Forwarded-For {remote_host}
   327→   327→            header_up X-Forwarded-Proto {scheme}
   328→   328→            header_up X-Real-IP {remote_host}
   329→   329→        }
   330→   330→    }
   331→   331→}
   332→   332→```
   333→   333→
   334→   334→### How It Works
   335→   335→
   336→   336→1. **XTransformPort Gateway** — If a request includes `?XTransformPort=<port>` in the query string, Caddy proxies to that port on localhost. This is useful in sandboxed / multi-tenant environments where the port is dynamically assigned.
   337→   337→
   338→   338→2. **Default Proxy** — All other requests are proxied to `localhost:3000` (the Next.js server).
   339→   339→
   340→   340→3. **Headers** — All proxy forwarding sets standard headers (`Host`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Real-IP`) so Next.js can correctly determine the original client information.
   341→   341→
   342→   342→### Production Domain Configuration
   343→   343→
   344→   344→Replace the port-based config with a domain-based one:
   345→   345→
   346→   346→```caddyfile
   347→   347→taskflow.yourdomain.com {
   348→   348→    reverse_proxy localhost:3000 {
   349→   349→        header_up Host {host}
   350→   350→        header_up X-Forwarded-For {remote_host}
   351→   351→        header_up X-Forwarded-Proto {scheme}
   352→   352→        header_up X-Real-IP {remote_host}
   353→   353→    }
   354→   354→}
   355→   355→```
   356→   356→
   357→   357→### Deploy the Caddyfile
   358→   358→
   359→   359→```bash
   360→   360→# Copy to Caddy's config location (if using system Caddy)
   361→   361→sudo cp /opt/taskflow/Caddyfile /etc/caddy/Caddyfile
   362→   362→
   363→   363→# Validate the configuration
   364→   364→sudo caddy validate --config /etc/caddy/Caddyfile
   365→   365→
   366→   366→# Reload Caddy (zero downtime)
   367→   367→sudo systemctl reload caddy
   368→   368→```

   372→   372→## 7. SSL & Domain Configuration
   373→   373→
   374→   374→### Automatic HTTPS with Caddy
   375→   375→
   376→   376→Caddy automatically provisions and renews SSL/TLS certificates from **Let's Encrypt** when you specify a domain name in the Caddyfile. No manual certificate management is required.
   377→   377→
   378→   378→### Setup Steps
   379→   379→
   380→   380→1. **Point your domain** to the server's public IP address via DNS (A record).
   381→   381→
   382→   382→2. **Update the Caddyfile** to use your domain:
   383→   383→
   384→   384→   ```caddyfile
   385→   385→   taskflow.yourdomain.com {
   386→   386→       reverse_proxy localhost:3000
   387→   387→   }
   388→   388→   ```
   389→   389→
   390→   390→3. **Ensure ports 80 and 443 are open** in your firewall:
   391→   391→
   392→   392→   ```bash
   393→   393→   sudo ufw allow 80/tcp
   394→   394→   sudo ufw allow 443/tcp
   395→   395→   ```
   396→   396→
   397→   397→4. **Reload Caddy** — certificates will be provisioned automatically on first request.
   398→   398→
   399→   399→### Custom Domain with Subdomain
   400→   400→
   401→   401→```caddyfile
   402→   402→# Main application
   403→   403→app.yourdomain.com {
   404→   404→    reverse_proxy localhost:3000
   405→   405→}
   406→   406→
   407→   407→# Optional: API subdomain
   408→   408→api.yourdomain.com {
   409→   409→    reverse_proxy localhost:3000
   410→   410→}
   411→   411→```
   412→   412→
   413→   413→### DNS Configuration
   414→   414→
   415→   415→| Type | Name | Value |
   416→   416→|---|---|---|
   417→   417→| A | `taskflow` (or `app`) | `<your-server-ip>` |
   418→   418→
   419→   419→Allow up to 5 minutes for DNS propagation after updating records.
   420→   420→
   421→   421→### Self-Signed Certificates (Development Only)
   422→   422→
   423→   423→For local development without a public domain, Caddy will use its internal CA. To trust it locally:
   424→   424→
   425→   425→```bash
   426→   426→caddy trust
   427→   427→```

   431→   431→## 8. Security Considerations
   432→   432→
   433→   433→### Current Security Model
   434→   434→
   435→   435→TaskFlow implements a **client-side session model** using Zustand. The authentication flow is:
   436→   436→
   437→   437→1. User submits credentials to `POST /api/login`
   438→   438→2. Server verifies email/password against the database
   439→   439→3. Server returns the user object (without the password hash) to the client
   440→   440→4. Client stores the user in Zustand state (in-memory, per tab)
   441→   441→5. The `RouteGuard` component checks the Zustand state before rendering protected routes
   442→   442→
   443→   443→#### Password Hashing
   444→   444→
   445→   445→Passwords are hashed using **SHA-256** via the Web Crypto API (`crypto.subtle.digest`).
   446→   446→
   447→   447→```typescript
   448→   448→// src/lib/auth.ts
   449→   449→export async function hashPassword(password: string): Promise<string> {
   450→   450→  const encoder = new TextEncoder()
   451→   451→  const data = encoder.encode(password)
   452→   452→  const hashBuffer = await crypto.subtle.digest('SHA-256', data)
   453→   453→  const hashArray = Array.from(new Uint8Array(hashBuffer))
   454→   454→  return hashArray.map(b => b.toString(16).padStart(2, '0')).join('')
   455→   455→}
   456→   456→```
   457→   457→
   458→   458→> **Production Warning:** SHA-256 without salting is **not** recommended for production password storage. See [Recommended Hardening](#recommended-production-hardening) below.
   459→   459→
   460→   460→### Client Data Isolation
   461→   461→
   462→   462→Client users can only see projects they are explicitly assigned to via the `ClientProject` join table:
   463→   463→
   464→   464→```
   465→   465→User (client) ←→ ClientProject ←→ Project
   466→   466→```
   467→   467→
   468→   468→- `john@client.com` is linked to 2 projects via `ClientProject` records
   469→   469→- `lisa@client.com` is linked to 1 project via `ClientProject` records
   470→   470→- API routes filter projects by `clientId` to enforce isolation
   471→   471→
   472→   472→### File Upload Restrictions
   473→   473→
   474→   474→| Restriction | Implementation |
   475→   475→|---|---|
   476→   476→| Max file size | 10 MB (`MAX_FILE_SIZE` in upload route) |
   477→   477→| Allowed types | Whitelist of 13 extensions (images, docs, archives) |
   478→   478→| Filename sanitization | Non-alphanumeric chars replaced with `_` |
   479→   479→| Unique filenames | UUID prefix prevents collisions |
   480→   480→| Directory traversal | `path.resolve()` + `startsWith()` check in serve route |
   481→   481→| File serving | Rewritten through API route, not served as static files |
   482→   482→
   483→   483→### API Access Patterns
   484→   484→
   485→   485→- **Registration** (`POST /api/register`): Requires a valid `adminUserId` — verifies the requester has admin role before creating users
   486→   486→- **Login** (`POST /api/login`): Checks user existence, password verification, and account status (`inactive` users are blocked)
   487→   487→- **Route Guard** (`RouteGuard` component): Client-side role check — supports `allowedRoles` prop to restrict UI sections
   488→   488→
   489→   489→### Recommended Production Hardening
   490→   490→
   491→   491→Apply these improvements before going to production:
   492→   492→
   493→   493→#### 1. Server-Side Session Management
   494→   494→
   495→   495→Replace the Zustand-only session with proper server-side sessions:
   496→   496→
   497→   497→```typescript
   498→   498→// Use httpOnly cookies + server-side session validation
   499→   499→// Consider: iron-session, jose (JWE), or a session table in SQLite
   500→   500→```
   501→   501→
   502→   502→#### 2. Password Hashing Upgrade
   503→   503→
   504→   504→Replace SHA-256 with bcrypt, scrypt, or Argon2:
   505→   505→
   506→   506→```bash
   507→   507→bun add bcryptjs @types/bcryptjs
   508→   508→```
   509→   509→
   510→   510→```typescript
   511→   511→import bcrypt from 'bcryptjs'
   512→   512→const hash = await bcrypt.hash(password, 12)
   513→   513→const valid = await bcrypt.compare(password, hash)
   514→   514→```
   515→   515→
   516→   516→#### 3. Rate Limiting
   517→   517→
   518→   518→Add rate limiting to all API routes, especially authentication endpoints:
   519→   519→
   520→   520→```typescript
   521→   521→// Consider: @upstash/ratelimit, or a simple in-memory/token-bucket approach
   522→   522→// Priority routes to protect: /api/login, /api/register
   523→   523→```
   524→   524→
   525→   525→#### 4. CSRF Protection
   526→   526→
   527→   527→Since there are no cookies currently, CSRF risk is low. When adding cookie-based sessions, implement CSRF tokens.
   528→   528→
   529→   529→#### 5. API Middleware

   858→   858→## 11. Architecture Overview
   859→   859→
   860→   860→### Request Flow
   861→   861→
   862→   862→```
   863→   863→┌─────────┐      ┌──────────────┐      ┌──────────────┐      ┌─────────┐
   864→   864→│  Client  │ ──▶ │    Caddy     │ ──▶  │   Next.js    │ ──▶  │ Prisma  │ ──▶ SQLite
   865→   865→│ (Browser)│ ◀── │  (Reverse    │ ◀──  │  (App Router │ ◀──  │  ORM    │ ◀── (file)
   866→   866→└─────────┘      │   Proxy)    │      │   + API)     │      └─────────┘
   867→   867→                 └──────────────┘      └──────────────┘
   868→   868→                       :81                :3000
   869→   869→```
   870→   870→
   871→   871→1. **Caddy** (port 81/80/443) receives the request, applies SSL termination, and proxies to Next.js.
   872→   872→2. **Next.js** (port 3000) handles routing — either serving static pages (React SSR/CSR) or routing to API handlers.
   873→   873→3. **API Routes** (`src/app/api/*/route.ts`) contain business logic, validation, and database queries.
   874→   874→4. **Prisma ORM** translates queries into optimized SQL.
   875→   875→5. **SQLite** stores all data in a single file on disk.
   876→   876→
   877→   877→### Client Isolation via ClientProject Join Table
   878→   878→
   879→   879→```
   880→   880→┌──────────┐     ┌───────────────┐     ┌──────────┐
   881→   881→│   User   │────▶│ ClientProject │◀────│ Project  │
   882→   882→│ (client) │     │  clientId     │     │          │
   883→   883→│          │     │  projectId    │     │          │
   884→   884→└──────────┘     └───────────────┘     └──────────┘
   885→   885→                       │
   886→   886→                       ▼
   887→   887→              Only projects where a
   888→   888→              ClientProject record exists
   889→   889→              for this clientId are visible
   890→   890→```
   891→   891→
   892→   892→- Client users call `GET /api/client/projects` which filters by their user ID
   893→   893→- The `ClientProject` table enforces a many-to-many relationship
   894→   894→- `john@client.com` → 2 projects, `lisa@client.com` → 1 project
   895→   895→
   896→   896→### File Upload Flow
   897→   897→
   898→   898→```
   899→   899→┌─────────┐   POST /api/upload   ┌──────────────┐   write   ┌────────────┐
   900→   900→│  Client  │ ──────────────────▶  │  Upload API  │ ────────▶ │ upload/    │
   901→   901→│ (Browser)│ ◀──────────────────  │  (10MB max,  │           │ {uuid}-    │
   902→   902→└─────────┘   { url: /upload/.. } │   13 exts)   │           │  filename  │
   903→   903→                                     │             │           └────────────┘
   904→   904→                                     └──────────────┘
   905→   905→                                           │
   906→   906→┌─────────┐   GET /upload/{file}  ┌───────▼──────┐   read    ┌────────────┐
   907→   907→│  Client  │ ──────────────────▶  │  Serve API   │ ────────▶ │ upload/    │
   908→   908→│ (Browser)│ ◀──────────────────  │  (path check,│           │ {uuid}-    │
   909→   909→└─────────┘   file bytes + headers│   MIME type) │           │  filename  │
   910→   910→                                     └───────▲──────┘           └────────────┘
   911→   911→                                             │
   912→   912→                          next.config.ts rewrite:
   913→   913→                          /upload/:path* → /api/upload/serve/:path*
   914→   914→```
   915→   915→
   916→   916→1. Client uploads via `POST /api/upload` (multipart form data).
   917→   917→2. Server validates file size (10 MB), extension (13 allowed), and generates a UUID-prefixed filename.
   918→   918→3. File is written to the `upload/` directory.
   919→   919→4. The server returns the public URL: `/upload/{uuid}-{filename}`.
   920→   920→5. Next.js `rewrites` in `next.config.ts` transparently map `/upload/*` to `/api/upload/serve/*`.
   921→   921→6. The serve route validates against directory traversal, reads the file, and returns it with proper `Content-Type` and `Content-Disposition` headers.
   922→   922→
   923→   923→### Mini Services Architecture
   924→   924→
   925→   925→The `mini-services/` directory is reserved for future microservice extensions (currently contains only a `.gitkeep` placeholder). Example use cases include:
   926→   926→
   927→   927→- **WebSocket service** — Real-time notifications and live updates (see `examples/websocket/` for reference implementations)
   928→   928→- **Background workers** — Email sending, report generation
   929→   929→- **Scheduled tasks** — Cron-based maintenance, data cleanup
   930→   930→
   931→   931→Each mini service would run as an independent process and communicate with the main Next.js application via HTTP or WebSocket connections.

  1062→  1062→### 13.6 Known Limitations (Deferred)
  1063→  1063→
  1064→  1064→The following items were identified but intentionally deferred as they require architectural changes:
  1065→  1065→
  1066→  1066→1. **No server-side authentication middleware** — All API routes trust client-supplied `userId`. Adding session/JWT middleware is a significant architectural change recommended for a future v1.1 release.
  1067→  1067→2. **Password hashing uses SHA-256** — Should be upgraded to bcrypt/scrypt for production. The current implementation works but is not industry best practice.
  1068→  1068→3. **`ignoreBuildErrors: true`** in next.config.ts — Type checking is bypassed at build time. Should be enabled after resolving remaining type issues.
  1069→  1069→4. **`reactStrictMode: false`** — Should be re-enabled and any double-render issues fixed.
  1070→  1070→5. **Prisma fields use plain strings instead of enums** — `role`, `status`, `priority` etc. should be Prisma enums for database-level validation.
