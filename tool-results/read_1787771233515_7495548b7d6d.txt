    68→## 2. Environment Variables
    69→
    70→TaskFlow uses a single required environment variable. Create a `.env` file in the project root.
    71→
    72→### Configuration
    73→
    74→```env
    75→# Required — Path to the SQLite database file
    76→DATABASE_URL=file:/path/to/taskflow/db/dev.db
    77→```
    78→
    79→| Variable | Required | Default | Description |
    80→|---|---|---|---|
    81→| `DATABASE_URL` | **Yes** | — | SQLite connection string. Must use the `file:` prefix followed by an absolute path. |
    82→| `NODE_ENV` | No | `development` | Set to `production` by the start script. Do not set manually. |
    83→
    84→### Example Production `.env`
    85→
    86→```env
    87→DATABASE_URL=file:/opt/taskflow/db/dev.db
    88→```
    89→
    90→> **Note:** The `bun run start` script in `package.json` automatically sets `NODE_ENV=production`. No additional environment variables are needed for a standard deployment.

   137→## 4. Production Build & Deployment
   138→
   139→### Build
   140→
   141→```bash
   142→bun run build
   143→```
   144→
   145→This command performs two steps:
   146→
   147→1. **`next build`** — Compiles the Next.js application in standalone output mode. All required dependencies, traces, and server code are bundled into `.next/standalone/`.
   148→2. **Asset copy** — Copies `.next/static` and `public/` into the standalone directory so all assets are self-contained:
   149→
   150→```bash
   151→cp -r .next/static .next/standalone/.next/
   152→cp -r public .next/standalone/
   153→```
   154→
   155→### Start the Production Server
   156→
   157→```bash
   158→bun run start
   159→```
   160→
   161→This runs:
   162→
   163→```bash
   164→NODE_ENV=production bun .next/standalone/server.js
   165→```
   166→
   167→The server listens on **port 3000** by default. Logs are written to both stdout and `server.log`.
   168→
   169→### Standalone Output Mode
   170→
   171→The `next.config.ts` sets `output: "standalone"`, which means:
   172→
   173→- The build produces a **self-contained server** in `.next/standalone/`
   174→- Only `node_modules` required at runtime are traced and included
   175→- No need to install `node_modules` on the production server after building
   176→- The standalone directory contains its own `node_modules/`, `.next/`, and `server.js`
   177→
   178→This is ideal for Docker containers, VMs, and bare-metal deployments where you want a minimal footprint.
   179→
   180→### File Storage Configuration
   181→
   182→Uploaded files are stored in the local `upload/` directory relative to the project root (`process.cwd()`).
   183→
   184→| Setting | Value |
   185→|---|---|
   186→| **Upload directory** | `upload/` (relative to CWD) |
   187→| **Max file size** | 10 MB |
   188→| **Allowed extensions** | `.jpg`, `.jpeg`, `.png`, `.gif`, `.webp`, `.svg`, `.pdf`, `.doc`, `.docx`, `.xls`, `.xlsx`, `.txt`, `.zip` |
   189→| **Filename format** | `{uuid}-{sanitized-original-name}` |
   190→| **Serving** | Rewritten via `next.config.ts`: `/upload/:path*` → `/api/upload/serve/:path*` |
   191→
   192→#### Important for Production
   193→
   194→After building with standalone mode, the `upload/` directory **must exist at the working directory** where the server runs. Ensure:
   195→
   196→```bash
   197→# Create the upload directory if it doesn't exist
   198→mkdir -p /opt/taskflow/upload
   199→
   200→# Set appropriate permissions
   201→chmod 750 /opt/taskflow/upload
   202→```
   203→
   204→When deploying the standalone build, the `upload/` directory must be **alongside** the standalone output, or you must set the working directory appropriately:
   205→
   206→```bash
   207→# Option A: Run from project root (upload/ is already there)
   208→cd /opt/taskflow
   209→NODE_ENV=production bun .next/standalone/server.js
   210→
   211→# Option B: If deploying only the standalone directory, symlink or copy upload/
   212→mkdir -p /opt/taskflow/.next/standalone/upload
   213→# Or bind-mount in Docker: -v /opt/taskflow/upload:/app/upload
   214→```

   218→## 5. Database
   219→
   220→### SQLite Setup
   221→
   222→TaskFlow uses SQLite via Prisma ORM. The database file is a single file on disk — no external database server required.
   223→
   224→- **Default location:** `db/dev.db`
   225→- **Configured via:** `DATABASE_URL` in `.env`
   226→
   227→### Schema Management
   228→
   229→#### Push Schema (Recommended for Development)
   230→
   231→Applies the Prisma schema to the database without creating migration files. Useful for rapid prototyping.
   232→
   233→```bash
   234→bun run db:push
   235→```
   236→
   237→#### Migrate (Recommended for Production)
   238→
   239→Creates and applies versioned migration files. Provides rollback capability.
   240→
   241→```bash
   242→# Create and apply a new migration
   243→bun run db:migrate
   244→
   245→# Reset the database (drops all data, re-applies all migrations)
   246→bun run db:reset
   247→```
   248→
   249→### Seeding
   250→
   251→Populate the database with demo data:
   252→
   253→```bash
   254→bun run prisma db seed
   255→```
   256→
   257→> **Warning:** Seeding will fail if the database already contains data (duplicate email unique constraints). Drop the database first or use `bun run db:reset` to start fresh.
   258→
   259→### Backup
   260→
   261→SQLite is a single file — backup is a simple copy operation.
   262→
   263→```bash
   264→# Create a timestamped backup
   265→cp /opt/taskflow/db/dev.db "/opt/taskflow/db/backup-$(date +%Y%m%d-%H%M%S).db"
   266→
   267→# Automated daily backup (add to crontab)
   268→crontab -e
   269→# Add this line (runs daily at 2 AM):
   270→0 2 * * * cp /opt/taskflow/db/dev.db "/opt/taskflow/db/backup-$(date +\%Y\%m\%d-\%H\%M\%S).db"
   271→```
   272→
   273→### Restore
   274→
   275→```bash
   276→# Stop the application first
   277→pm2 stop taskflow  # or kill the process
   278→
   279→# Replace the database file
   280→cp /opt/taskflow/db/backup-20250701-020000.db /opt/taskflow/db/dev.db
   281→
   282→# Restart the application
   283→pm2 start taskflow
   284→```
   285→
   286→### Inspecting the Database
   287→
   288→```bash
   289→sqlite3 /opt/taskflow/db/dev.db
   290→

   292→.tables
   293→.schema User
   294→SELECT email, role, status FROM User;
   295→.quit
   296→```

   300→## 6. Caddy / Reverse Proxy Configuration
   301→
   302→### Overview
   303→
   304→TaskFlow includes a `Caddyfile` that configures Caddy as a reverse proxy. The current configuration uses the **XTransformPort gateway pattern** for dynamic port routing.
   305→
   306→### Current Caddyfile
   307→
   308→```caddyfile
   309→:81 {
   310→    @transform_port_query {
   311→        query XTransformPort=*
   312→    }
   313→
   314→    handle @transform_port_query {
   315→        reverse_proxy localhost:{query.XTransformPort} {
   316→            header_up Host {host}
   317→            header_up X-Forwarded-For {remote_host}
   318→            header_up X-Forwarded-Proto {scheme}
   319→            header_up X-Real-IP {remote_host}
   320→        }
   321→    }
   322→
   323→    handle {
   324→        reverse_proxy localhost:3000 {
   325→            header_up Host {host}
   326→            header_up X-Forwarded-For {remote_host}
   327→            header_up X-Forwarded-Proto {scheme}
   328→            header_up X-Real-IP {remote_host}
   329→        }
   330→    }
   331→}
   332→```
   333→
   334→### How It Works
   335→
   336→1. **XTransformPort Gateway** — If a request includes `?XTransformPort=<port>` in the query string, Caddy proxies to that port on localhost. This is useful in sandboxed / multi-tenant environments where the port is dynamically assigned.
   337→
   338→2. **Default Proxy** — All other requests are proxied to `localhost:3000` (the Next.js server).
   339→
   340→3. **Headers** — All proxy forwarding sets standard headers (`Host`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Real-IP`) so Next.js can correctly determine the original client information.
   341→
   342→### Production Domain Configuration
   343→
   344→Replace the port-based config with a domain-based one:
   345→
   346→```caddyfile
   347→taskflow.yourdomain.com {
   348→    reverse_proxy localhost:3000 {
   349→        header_up Host {host}
   350→        header_up X-Forwarded-For {remote_host}
   351→        header_up X-Forwarded-Proto {scheme}
   352→        header_up X-Real-IP {remote_host}
   353→    }
   354→}
   355→```
   356→
   357→### Deploy the Caddyfile
   358→
   359→```bash
   360→# Copy to Caddy's config location (if using system Caddy)
   361→sudo cp /opt/taskflow/Caddyfile /etc/caddy/Caddyfile
   362→
   363→# Validate the configuration
   364→sudo caddy validate --config /etc/caddy/Caddyfile
   365→
   366→# Reload Caddy (zero downtime)
   367→sudo systemctl reload caddy
   368→```

   372→## 7. SSL & Domain Configuration
   373→
   374→### Automatic HTTPS with Caddy
   375→
   376→Caddy automatically provisions and renews SSL/TLS certificates from **Let's Encrypt** when you specify a domain name in the Caddyfile. No manual certificate management is required.
   377→
   378→### Setup Steps
   379→
   380→1. **Point your domain** to the server's public IP address via DNS (A record).
   381→
   382→2. **Update the Caddyfile** to use your domain:
   383→
   384→   ```caddyfile
   385→   taskflow.yourdomain.com {
   386→       reverse_proxy localhost:3000
   387→   }
   388→   ```
   389→
   390→3. **Ensure ports 80 and 443 are open** in your firewall:
   391→
   392→   ```bash
   393→   sudo ufw allow 80/tcp
   394→   sudo ufw allow 443/tcp
   395→   ```
   396→
   397→4. **Reload Caddy** — certificates will be provisioned automatically on first request.
   398→
   399→### Custom Domain with Subdomain
   400→
   401→```caddyfile
   402→# Main application
   403→app.yourdomain.com {
   404→    reverse_proxy localhost:3000
   405→}
   406→
   407→# Optional: API subdomain
   408→api.yourdomain.com {
   409→    reverse_proxy localhost:3000
   410→}
   411→```
   412→
   413→### DNS Configuration
   414→
   415→| Type | Name | Value |
   416→|---|---|---|
   417→| A | `taskflow` (or `app`) | `<your-server-ip>` |
   418→
   419→Allow up to 5 minutes for DNS propagation after updating records.
   420→
   421→### Self-Signed Certificates (Development Only)
   422→
   423→For local development without a public domain, Caddy will use its internal CA. To trust it locally:
   424→
   425→```bash
   426→caddy trust
   427→```

   431→## 8. Security Considerations
   432→
   433→### Current Security Model
   434→
   435→TaskFlow implements a **client-side session model** using Zustand. The authentication flow is:
   436→
   437→1. User submits credentials to `POST /api/login`
   438→2. Server verifies email/password against the database
   439→3. Server returns the user object (without the password hash) to the client
   440→4. Client stores the user in Zustand state (in-memory, per tab)
   441→5. The `RouteGuard` component checks the Zustand state before rendering protected routes
   442→
   443→#### Password Hashing
   444→
   445→Passwords are hashed using **SHA-256** via the Web Crypto API (`crypto.subtle.digest`).
   446→
   447→```typescript
   448→// src/lib/auth.ts
   449→export async function hashPassword(password: string): Promise<string> {
   450→  const encoder = new TextEncoder()
   451→  const data = encoder.encode(password)
   452→  const hashBuffer = await crypto.subtle.digest('SHA-256', data)
   453→  const hashArray = Array.from(new Uint8Array(hashBuffer))
   454→  return hashArray.map(b => b.toString(16).padStart(2, '0')).join('')
   455→}
   456→```
   457→
   458→> **Production Warning:** SHA-256 without salting is **not** recommended for production password storage. See [Recommended Hardening](#recommended-production-hardening) below.
   459→
   460→### Client Data Isolation
   461→
   462→Client users can only see projects they are explicitly assigned to via the `ClientProject` join table:
   463→
   464→```
   465→User (client) ←→ ClientProject ←→ Project
   466→```
   467→
   468→- `john@client.com` is linked to 2 projects via `ClientProject` records
   469→- `lisa@client.com` is linked to 1 project via `ClientProject` records
   470→- API routes filter projects by `clientId` to enforce isolation
   471→
   472→### File Upload Restrictions
   473→
   474→| Restriction | Implementation |
   475→|---|---|
   476→| Max file size | 10 MB (`MAX_FILE_SIZE` in upload route) |
   477→| Allowed types | Whitelist of 13 extensions (images, docs, archives) |
   478→| Filename sanitization | Non-alphanumeric chars replaced with `_` |
   479→| Unique filenames | UUID prefix prevents collisions |
   480→| Directory traversal | `path.resolve()` + `startsWith()` check in serve route |
   481→| File serving | Rewritten through API route, not served as static files |
   482→
   483→### API Access Patterns
   484→
   485→- **Registration** (`POST /api/register`): Requires a valid `adminUserId` — verifies the requester has admin role before creating users
   486→- **Login** (`POST /api/login`): Checks user existence, password verification, and account status (`inactive` users are blocked)
   487→- **Route Guard** (`RouteGuard` component): Client-side role check — supports `allowedRoles` prop to restrict UI sections
   488→
   489→### Recommended Production Hardening
   490→
   491→Apply these improvements before going to production:
   492→
   493→#### 1. Server-Side Session Management
   494→
   495→Replace the Zustand-only session with proper server-side sessions:
   496→
   497→```typescript
   498→// Use httpOnly cookies + server-side session validation
   499→// Consider: iron-session, jose (JWE), or a session table in SQLite
   500→```
   501→
   502→#### 2. Password Hashing Upgrade
   503→
   504→Replace SHA-256 with bcrypt, scrypt, or Argon2:
   505→
   506→```bash
   507→bun add bcryptjs @types/bcryptjs
   508→```
   509→
   510→```typescript
   511→import bcrypt from 'bcryptjs'
   512→const hash = await bcrypt.hash(password, 12)
   513→const valid = await bcrypt.compare(password, hash)
   514→```
   515→
   516→#### 3. Rate Limiting
   517→
   518→Add rate limiting to all API routes, especially authentication endpoints:
   519→
   520→```typescript
   521→// Consider: @upstash/ratelimit, or a simple in-memory/token-bucket approach
   522→// Priority routes to protect: /api/login, /api/register
   523→```
   524→
   525→#### 4. CSRF Protection
   526→
   527→Since there are no cookies currently, CSRF risk is low. When adding cookie-based sessions, implement CSRF tokens.
   528→
   529→#### 5. API Middleware
   530→
   531→Create a Next.js middleware (`src/middleware.ts`) for:
   532→
   533→- Authentication verification on all `/api/*` routes
   534→- Request logging
   535→- IP-based rate limiting
   536→- CORS configuration
   537→
   538→#### 6. Remove Demo Accounts
   539→
   540→Before production deployment, either remove the seeded demo accounts or change their passwords:
   541→
   542→```bash
   543→# Option A: Fresh database without seed data
   544→rm /opt/taskflow/db/dev.db
   545→bun run db:push
   546→# Create admin user manually via the registration API
   547→
   548→# Option B: Change demo passwords via SQLite
   549→sqlite3 /opt/taskflow/db/dev.db
   550→UPDATE User SET password = '<new-bcrypt-hash>' WHERE email = 'admin@taskflow.com';
   551→```
   552→
   553→#### 7. File Upload Hardening
   554→
   555→- Add authentication check to `POST /api/upload`
   556→- Add authentication check to `GET /api/upload/serve/[path]`
   557→- Consider virus scanning for uploaded files
   558→- Set `Content-Disposition: attachment` for non-image files to prevent XSS
   559→
   560→#### 8. Environment Isolation
   561→
   562→- Never commit `.env` to version control (already in `.gitignore`)
   563→- Use different `DATABASE_URL` paths for dev/staging/production
   564→- Restrict file permissions: `chmod 600 .env`

   568→## 9. Monitoring & Maintenance
   569→
   570→### Health Check
   571→
   572→There is no dedicated `/api/health` endpoint yet. Monitor availability by checking the root URL:
   573→
   574→```bash
   575→curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/
   576→# Returns 200 if the server is running
   577→```
   578→
   579→To add a proper health endpoint, create `src/app/api/health/route.ts`:
   580→
   581→```typescript
   582→import { NextResponse } from 'next/server'
   583→
   584→export async function GET() {
   585→  return NextResponse.json({ status: 'ok', timestamp: new Date().toISOString() })
   586→}
   587→```
   588→
   589→### Process Management
   590→
   591→Use **PM2** or **systemd** to keep the application running and auto-restart on crashes.
   592→
   593→#### PM2 Setup
   594→
   595→```bash
   596→bun add -g pm2
   597→
   598→# Create ecosystem.config.js in project root
   599→cat > /opt/taskflow/ecosystem.config.js << 'EOF'
   600→module.exports = {
   601→  apps: [{
   602→    name: 'taskflow',
   603→    script: '.next/standalone/server.js',
   604→    cwd: '/opt/taskflow',
   605→    interpreter: 'bun',
   606→    env: { NODE_ENV: 'production' },
   607→    instances: 1,
   608→    autorestart: true,
   609→    max_memory_restart: '512M',
   610→    error_file: '/opt/taskflow/logs/error.log',
   611→    out_file: '/opt/taskflow/logs/out.log',
   612→    log_date_format: 'YYYY-MM-DD HH:mm:ss Z',
   613→  }]
   614→}
   615→EOF
   616→
   617→# Start
   618→pm2 start ecosystem.config.js
   619→pm2 save
   620→pm2 startup  # generates startup script
   621→```
   622→
   623→#### systemd Service
   624→
   625→```ini
   626→# /etc/systemd/system/taskflow.service
   627→[Unit]
   628→Description=TaskFlow Application
   629→After=network.target
   630→
   631→[Service]
   632→Type=simple
   633→User=www-data
   634→WorkingDirectory=/opt/taskflow
   635→ExecStart=/home/<user>/.bun/bin/bun .next/standalone/server.js
   636→Environment=NODE_ENV=production
   637→Restart=on-failure
   638→RestartSec=5
   639→
   640→[Install]
   641→WantedBy=multi-user.target
   642→```
   643→
   644→```bash
   645→sudo systemctl daemon-reload
   646→sudo systemctl enable taskflow
   647→sudo systemctl start taskflow
   648→```

   652→| Log | Location | Description |

   716→## 10. Troubleshooting
   717→
   718→### Common Issues & Solutions
   719→
   720→#### Port 3000 Already in Use
   721→
   722→```
   723→Error: listen EADDRINUSE: address already in use :::3000
   724→```
   725→
   726→**Solution:**
   727→
   728→```bash
   729→# Find the process using port 3000
   730→lsof -i :3000
   731→# or
   732→ss -tlnp | grep 3000
   733→
   734→# Kill the process
   735→kill <PID>
   736→
   737→# Or use a different port
   738→PORT=3001 bun run start
   739→```
   740→
   741→#### Database Locked or Corruption
   742→
   743→```
   744→Error: SQLITE_BUSY: database is locked
   745→```
   746→
   747→**Solution:**
   748→
   749→```bash
   750→# 1. Stop the application
   751→pm2 stop taskflow
   752→
   753→# 2. Check for stale lock files
   754→ls -la /opt/taskflow/db/
   755→
   756→# 3. Run integrity check
   757→sqlite3 /opt/taskflow/db/dev.db "PRAGMA integrity_check;"
   758→
   759→# 4. If corrupted, restore from backup
   760→cp /opt/taskflow/db/backup-<latest>.db /opt/taskflow/db/dev.db
   761→
   762→# 5. Restart
   763→pm2 start taskflow
   764→```
   765→
   766→#### Prisma Client Not Generated
   767→
   768→```
   769→Error: @prisma/client did not initialize yet
   770→```
   771→
   772→**Solution:**
   773→
   774→```bash
   775→bun run db:generate
   776→# Then restart the server
   777→```
   778→
   779→#### Build Fails — Module Not Found
   780→
   781→```
   782→Error: Cannot find module '...'
   783→```
   784→
   785→**Solution:**
   786→
   787→```bash
   788→rm -rf node_modules .next
   789→bun install
   790→bun run build
   791→```
   792→
   793→#### Uploaded Files Not Accessible
   794→
   795→**Symptoms:** Uploads succeed (200 response) but files return 404 when accessed via `/upload/<filename>`.
   796→
   797→**Solution:**
   798→
   799→1. Verify the `upload/` directory exists at the server's working directory:
   800→
   801→   ```bash
   802→   ls -la /opt/taskflow/upload/
   803→   ```
   804→
   805→2. If using standalone mode, ensure the rewrite is working. The `next.config.ts` rewrites `/upload/:path*` to `/api/upload/serve/:path*`. In standalone mode, this rewrite is part of the compiled server.
   806→
   807→3. Check file permissions:
   808→
   809→   ```bash
   810→   chmod 755 /opt/taskflow/upload/
   811→   chmod 644 /opt/taskflow/upload/*
   812→   ```
   813→
   814→#### Caddy 502 Bad Gateway
   815→
   816→**Cause:** Next.js server is not running or not listening on the expected port.
   817→
   818→```bash
   819→# Check if Next.js is running
   820→curl http://localhost:3000/
   821→
   822→# Check Caddy status
   823→sudo systemctl status caddy
   824→
   825→# Check Caddy logs
   826→sudo journalctl -u caddy --since "5 minutes ago"
   827→```
   828→
   829→#### Blank Page After Deployment
   830→
   831→**Cause:** Static assets not copied into the standalone directory.
   832→
   833→```bash
   834→# Verify assets exist
   835→ls /opt/taskflow/.next/standalone/.next/static/
   836→ls /opt/taskflow/.next/standalone/public/
   837→
   838→# If missing, copy them manually
   839→cp -r /opt/taskflow/.next/static /opt/taskflow/.next/standalone/.next/
   840→cp -r /opt/taskflow/public /opt/taskflow/.next/standalone/
   841→
   842→# Restart
   843→pm2 restart taskflow
   844→```
   845→
   846→#### SQLite WAL Mode (Recommended for Production)
   847→
   848→Improve concurrent read performance and reduce locking issues:
   849→
   850→```bash
   851→sqlite3 /opt/taskflow/db/dev.db "PRAGMA journal_mode=WAL;"
   852→```
   853→
   854→Consider adding this to your `prisma/schema.prisma` or applying it as a post-deployment step.

   858→## 11. Architecture Overview
   859→
   860→### Request Flow
   861→
   862→```
   863→┌─────────┐      ┌──────────────┐      ┌──────────────┐      ┌─────────┐
   864→│  Client  │ ──▶ │    Caddy     │ ──▶  │   Next.js    │ ──▶  │ Prisma  │ ──▶ SQLite
   865→│ (Browser)│ ◀── │  (Reverse    │ ◀──  │  (App Router │ ◀──  │  ORM    │ ◀── (file)
   866→└─────────┘      │   Proxy)    │      │   + API)     │      └─────────┘
   867→                 └──────────────┘      └──────────────┘
   868→                       :81                :3000
   869→```
   870→
   871→1. **Caddy** (port 81/80/443) receives the request, applies SSL termination, and proxies to Next.js.
   872→2. **Next.js** (port 3000) handles routing — either serving static pages (React SSR/CSR) or routing to API handlers.
   873→3. **API Routes** (`src/app/api/*/route.ts`) contain business logic, validation, and database queries.
   874→4. **Prisma ORM** translates queries into optimized SQL.
   875→5. **SQLite** stores all data in a single file on disk.
   876→
   877→### Client Isolation via ClientProject Join Table
   878→
   879→```
   880→┌──────────┐     ┌───────────────┐     ┌──────────┐
   881→│   User   │────▶│ ClientProject │◀────│ Project  │
   882→│ (client) │     │  clientId     │     │          │
   883→│          │     │  projectId    │     │          │
   884→└──────────┘     └───────────────┘     └──────────┘
   885→                       │
   886→                       ▼
   887→              Only projects where a
   888→              ClientProject record exists
   889→              for this clientId are visible
   890→```
   891→
   892→- Client users call `GET /api/client/projects` which filters by their user ID
   893→- The `ClientProject` table enforces a many-to-many relationship
   894→- `john@client.com` → 2 projects, `lisa@client.com` → 1 project
   895→
   896→### File Upload Flow
   897→
   898→```
   899→┌─────────┐   POST /api/upload   ┌──────────────┐   write   ┌────────────┐
   900→│  Client  │ ──────────────────▶  │  Upload API  │ ────────▶ │ upload/    │
   901→│ (Browser)│ ◀──────────────────  │  (10MB max,  │           │ {uuid}-    │
   902→└─────────┘   { url: /upload/.. } │   13 exts)   │           │  filename  │
   903→                                     │             │           └────────────┘
   904→                                     └──────────────┘
   905→                                           │
   906→┌─────────┐   GET /upload/{file}  ┌───────▼──────┐   read    ┌────────────┐
   907→│  Client  │ ──────────────────▶  │  Serve API   │ ────────▶ │ upload/    │
   908→│ (Browser)│ ◀──────────────────  │  (path check,│           │ {uuid}-    │
   909→└─────────┘   file bytes + headers│   MIME type) │           │  filename  │
   910→                                     └───────▲──────┘           └────────────┘
   911→                                             │
   912→                          next.config.ts rewrite:
   913→                          /upload/:path* → /api/upload/serve/:path*
   914→```
   915→
   916→1. Client uploads via `POST /api/upload` (multipart form data).
   917→2. Server validates file size (10 MB), extension (13 allowed), and generates a UUID-prefixed filename.
   918→3. File is written to the `upload/` directory.
   919→4. The server returns the public URL: `/upload/{uuid}-{filename}`.
   920→5. Next.js `rewrites` in `next.config.ts` transparently map `/upload/*` to `/api/upload/serve/*`.
   921→6. The serve route validates against directory traversal, reads the file, and returns it with proper `Content-Type` and `Content-Disposition` headers.
   922→
   923→### Mini Services Architecture
   924→
   925→The `mini-services/` directory is reserved for future microservice extensions (currently contains only a `.gitkeep` placeholder). Example use cases include:
   926→
   927→- **WebSocket service** — Real-time notifications and live updates (see `examples/websocket/` for reference implementations)
   928→- **Background workers** — Email sending, report generation
   929→- **Scheduled tasks** — Cron-based maintenance, data cleanup
   930→
   931→Each mini service would run as an independent process and communicate with the main Next.js application via HTTP or WebSocket connections.
   932→

  1049→### 13.6 Known Limitations (Deferred)
  1050→
  1051→The following items were identified but intentionally deferred as they require architectural changes:
  1052→
  1053→1. **No server-side authentication middleware** — All API routes trust client-supplied `userId`. Adding session/JWT middleware is a significant architectural change recommended for a future v1.1 release.
  1054→2. **Password hashing uses SHA-256** — Should be upgraded to bcrypt/scrypt for production. The current implementation works but is not industry best practice.
  1055→3. **`ignoreBuildErrors: true`** in next.config.ts — Type checking is bypassed at build time. Should be enabled after resolving remaining type issues.
  1056→4. **`reactStrictMode: false`** — Should be re-enabled and any double-render issues fixed.
  1057→5. **Prisma fields use plain strings instead of enums** — `role`, `status`, `priority` etc. should be Prisma enums for database-level validation.
